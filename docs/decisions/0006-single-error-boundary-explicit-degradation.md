# 0006 エラー境界は 1 箇所、縮退は明示的にオプトインする

関連 Issue: #59 / #68

## 背景

失敗には 2 種類ある。Wake Lock やタイマー音のように失敗しても該当機能を諦めるだけで済むものと、IndexedDB の読み書き失敗や実装バグのように「動いているが表示が事実と違う」状態を生むものである。後者を画面ごとに catch して空表示にすると、記録が無いのか読めないのか区別できなくなる。

## 決定

- 判断基準は「この失敗は根幹（トレーニングを実行して実績を記録し、それを正しく見せること）を壊すか」
- 壊す・不明な失敗は画面で catch せず、境界 1 箇所（`installErrorBoundary` の 4 配線: `app.config.errorHandler` / `router.onError` / `unhandledrejection` / `window` の `error`）で受けて全画面のエラー画面に切り替える
- 壊さない失敗（縮退）だけを呼び出し元で catch して継続し、spec の根拠をコメントに書く（明示的なオプトイン）。分類に迷ったら catch しない
- 縮退がブラウザ API の glue に閉じる場合は composable 側で握り切り、呼び出し元に catch を分散させない

## 検討した代替案

- **画面ごとに try / catch して部分的に縮退する**: catch の分類が画面ごとにぶれ、握りつぶしが混ざる。「読み取り失敗を未記録と同じ空表示にする」誤りを構造的に防げない
- **縮退をデフォルトにし、致命扱いを明示する**: 分類漏れが「動いているが事実と違う」側に落ちる。逆（致命がデフォルト）なら分類漏れは自動でエラー画面に落ちるため安全側
- **恒久故障向けの復旧 UI（データ削除など）を用意する**: quota 超過や object store 破損は RELOAD では回復しないが、復旧はブラウザのサイトデータ削除に委ねる。個人用アプリで復旧 UI を維持するコストに見合わない

## 帰結

- Service Worker 登録失敗のように自動注入コードが未処理 reject を出すものは、境界で fatal 化しないよう握る（#68）
- 境界の最終防波堤 `report()` は入力の文字列化でも throw しない（`Object.create(null)` のような値でも Unknown error に落とす）
- ユーザーが与えた入力の不正（Import ファイルの検証）は失敗ではなく結果の 1 つとして値で返し、例外と混ぜない
- 仕様の正本は [docs/spec.md](../spec.md) の「エラーハンドリング」節
